### 1.4 PTQ1_0 and PQ2_0 block layouts (from ggml-org/llama.cpp PR #29077, verbatim)

```c
#define QK_PQ2_0 128
typedef struct {
    ggml_half d;                 // scale for the 128 weights in this block
    uint8_t   qs[QK_PQ2_0 / 4];  // 2 bits per weight
} block_pq2_0;                   // 34 bytes
// weight j: q = (qs[j/4] >> ((j%4)*2)) & 3;  value = (q - 1) * d;   (00=-1, 01=0, 10=+1, 11 unused)

#define QK_PTQ1_0 128
typedef struct {
    uint8_t   qs[24];   // 5 trits per byte, 120 values
    uint8_t   qh[2];    // 4 trits per byte,   8 values
    ggml_half d;        // scale for this block
} block_ptq1_0;         // 28 bytes  (matches the file: 1120 bytes per row of 5120)

static const size_t ptq1_0_stages[3] = {32, 16, 8};
void dequantize_row_ptq1_0(const block_ptq1_0 * x, float * y, int64_t k) {
    const uint8_t pow3[6] = {1, 3, 9, 27, 81, 243};
    for (int64_t i = 0; i < k / 128; ++i) {
        const float d = fp16_to_fp32(x[i].d);
        size_t j = 0;
        for (size_t s = 0; s < 3; ++s) {
            const size_t c = ptq1_0_stages[s];
            for (; j + c <= 24; j += c) {
                for (size_t n = 0; n < 5; ++n)
                    for (size_t m = 0; m < c; ++m) {
                        const uint8_t q  = x[i].qs[j + m] * pow3[n];
                        const int16_t xi = ((uint16_t) q * 3) >> 8;      // most-significant trit first
                        *y++ = (float) (xi - 1) * d;
                    }
            }
        }
        for (size_t n = 0; n < 4; ++n)
            for (size_t h = 0; h < 2; ++h) {
                const uint8_t q  = x[i].qh[h] * pow3[n];
                const int16_t xi = ((uint16_t) q * 3) >> 8;
                *y++ = (float) (xi - 1) * d;
            }
    }
}
```

Note the output order: with 24 = 16 + 8 the stage loop runs `c = 16` (bytes 0..15) then `c = 8`
(bytes 16..23), each emitting 5 × c values (trit n of byte m, n outer, m inner), then `qh` emits
4 × 2 values. The converter ports this loop verbatim to numpy and must be validated by the test in
section 6.4 (never re-derive the order by hand).

### 1.5 The Hadamard rotation (CONTRACT)

`H` is the normalized Sylvester Walsh–Hadamard matrix of order 1024 in natural (Sylvester)
ordering, `H = (1/32) · H_2^{⊗10}`, `H_2 = [[1, 1], [1, -1]]`. It is symmetric and involutory
(`H·H = I`), so the inverse is `H` itself. It is applied blockwise over consecutive 1024-element
blocks of the input axis; `s_w` is the ±1 sign vector of width `w`, indexed by absolute position in
the row (`signs[block*1024 + idx]`).

- Folded projection (every tensor in `weight_names`): `y = W' · H_blk(s_w ⊙ x)`, i.e. signs are
  applied BEFORE the butterfly (bonsai-vllm `kernels.cu`: `buf[idx] = x[...] * signs[col0+idx]`,
  10 butterfly stages, then `* 0.03125f`). `W'` is the ternary tensor as stored.
- Embedding (`inverse_weight_names`): after the row gather `z = E'[token]`, restore the primal
  basis with `h = s_5120 ⊙ H_blk(z)`. Only `token_embd.weight`.
- `gdn_v_grouped = true` (runtime activation permutation only for `ssm_out.weight`; for STORAGE order the same 48-head permutation `perm[i] = 3*(i % 16) + i // 16` also applies to `dt_bias`, `ssm_conv1d` value columns and `attn_gate` output rows, see section 9 and `bonsai-ternary-conversion.md`): the folded weight expects its 6144-wide
  input in "grouped" value-head order. llama.cpp's own GDN emits the tiled order `[hd=128][nk=16]
  [rep=3]` and therefore permutes the activation to `[hd][rep][nk]` before the sign/Hadamard step.
  Grouped order means value head `j = rep + 3·k_head`, i.e. value heads that share a key head are
  consecutive, which is HF's `repeat_interleave` order. Agent B must check the order NInfer's GDN
  output kernel writes for `out_proj` (see section 5.3); if it is already HF order no runtime
  permutation is needed. A permutation, if needed, is a gather inside the Hadamard prologue, never
  a separate kernel, and can NOT be folded into `W'` (it acts before `H`).
- The residual stream, norms, GDN recurrent state, attention KV and the MTP/DFlash2 heads are all
  in the primal basis. Rotation is local to each projection input.

Reference numpy for tests (agent A ships this in `tools/convert/quantization/hadamard.py`):

```python
def sylvester_hadamard(n):            # n power of two; returns n×n float64, normalized
    h = np.array([[1.0]])
    while h.shape[0] < n:
        h = np.block([[h, h], [h, -h]])
    return h / np.sqrt(n)

def rotate_rows(x, signs, block=1024):   # x: [T, K]; forward transform for projections
    h = sylvester_hadamard(block)
    xs = (x * signs[None, :]).reshape(x.shape[0], -1, block)
    return (xs @ h.T).reshape(x.shape)   # h symmetric, so h.T == h

def unrotate_embedding_rows(z, signs, block=1024):  # inverse for token_embd
    h = sylvester_hadamard(block)
    return (z.reshape(z.shape[0], -1, block) @ h.T).reshape(z.shape) * signs[None, :]
```

Offline identity used by the M0 test: `W_orig ≈ W' · diag(s) ⊙ H`, more precisely
`W_orig[:, blk] ≈ (W'[:, blk] @ H) * s[blk]` per 1024-block, where `W'` is the dequantized ternary
tensor `(q - 1) * scale`. The reconstruction error must be consistent with 1.76-bit quantization
(cosine similarity per row well above 0.9); a sign or ordering mistake shows up as ~0 similarity.

## 2. NInfer weight format `t2_g128_fp16` (CONTRACT)

Name follows the artifact convention (`q4_g64_fp16`, `q8_g32_fp16`, `q5_g64_fp16`): `t2` = ternary
in 2-bit slots, group 128, fp16 scales. Owner of the definition: agent B; agent A writes it; agent
C reads it.

Per matrix of `N` output rows × `K` input columns (`K % 128 == 0`; rotated inputs additionally have
`K % 1024 == 0`):

| plane | dtype / shape | layout |
|---|---|---|
| `codes` | `uint8 [N][K/4]` | row-major, K-contiguous; weight `(n, k)` is `(codes[n][k/4] >> ((k%4)*2)) & 3`; value `= code - 1`; code 3 is invalid. Bit-identical to a PQ2_0 row with the scales stripped, and to bonsai-vllm's little-endian int32 words (16 codes per word). |
| `scales` | `fp16 [N][K/128]` | row-major; scale of group `g` covers `k ∈ [128g, 128g+128)`. |
| `weight_scale_divisor` | as the existing formats use it | 1.0 (scales are absolute). |

Row-level fusions and permutations (fused qkv, fused gate+up, q/gate interleave, GDN value-head
order) are done exactly as the converter does them for bf16/q8 today: permute whole rows of
`codes` and `scales` together. Nothing in `t2_g128_fp16` is tile-reordered in v1. If agent C's GEMV
wants a tile-major layout, that becomes a second format (`t2r_…`) added later with a reorder pass
in the converter; do not block M1 on it.

Hadamard side data, stored once in the artifact as direct `bf16 [width]` text parameters, in
the primal index order of the activation NInfer feeds the projection (logical parameter names
are what the loader binds; the converter writes exactly these):

| parameter | width | used by |
|---|---|---|
| `text/hadamard/signs_5120` | 5120 | inputs of gdn in_proj (qkv+z fused), attention qkv fused, mlp gate+up fused, lm_head (M5); inverse for embeddings (M5) |
| `text/hadamard/signs_6144` | 6144 | inputs of gdn out_proj and attention o_proj |
| `text/hadamard/signs_17408` | 17408 | input of mlp down_proj |

Text-config metadata (`components.text.config.prism_hadamard`, next to the existing config
keys; `rotated_inputs` lists the per-layer parameter suffixes stored as `t2_g128_fp16`):


### 2.1 Which tensors are `t2_g128_fp16`

NInfer names its logical parameters per projection and lets the recipe decide how they are packed
into artifact objects ("parents"); the engine then requires fused projections to be adjacent rows
of ONE parent (`src/core/weight_view.cpp:157-173`, `contiguous_weight_region`). The 27B recipe
today uses a paired form for the input projections (q4 parent + q5 parent); `t2` uses the
single-parent form that NVFP4/FP8 use, so every fused projection is one object:

| NInfer parameters (`text/layers/{i}/…`) | one `t2` parent, rows in this order | (N, K) | GGUF source rows |
|---|---|---|---|
| `gdn/query`, `gdn/key`, `gdn/value`, `gdn/z` | query 2048, key 2048, value 6144, z 6144 | 16384 × 5120 | `attn_qkv` rows 0..10240 then `attn_gate` |
| `gdn/output` | — | 5120 × 6144 | `ssm_out` |
| `attention/query`, `attention/key`, `attention/gate`, `attention/value` | query 6144, key 1024, gate 6144, value 1024 | 14336 × 5120 | `attn_q` de-interleaved into query/gate rows exactly as `tools/convert/qwen3_5.py:499-512` does today, `attn_k`, `attn_v` |
| `attention/output` | — | 5120 × 6144 | `attn_output` |
| `mlp/gate`, `mlp/up` | gate 17408, up 17408 | 34816 × 5120 | `ffn_gate`, `ffn_up` |
| `mlp/down` | — | 5120 × 17408 | `ffn_down` |
| `text/output_head` | — | 248320 × 5120 | `output` (v1: dequantized, folded, `q8_g32_fp16`; M5: `t2`) |
| `text/token_embedding` | — | 248320 × 5120 | `token_embd` (v1: dequantized, un-rotated, `q8_g32_fp16`) |

Row-level fusion for `t2` is a plain row concatenation of `codes` and `scales`, so the converter
reuses the existing parameter registration (`qwen3_5.py` `attention`/`gdn`/`dense` builders) and
the recipe's `group()` to force the single parent (`tools/convert/recipe.py:241-243`).

Unchanged formats (copied from the GGUF, F32→bf16/fp32 as the existing artifact stores them):
`in_proj_a`, `in_proj_b` (bf16 48×5120 each, the `gdn_gating_proj` family), `A_log`, `dt_bias`,
`conv1d`, all norms, `q_norm`/`k_norm`.

Copied from `E:\LLM\qwen3_8_27b.ninfer`: the whole `mtp` component and `dflash2` component
(and `dflash_config`), unchanged.

### 2.2 Embedding and lm_head in v1 (GUIDANCE, chosen for M1 speed)

- Embedding: dequantize `token_embd` offline, apply the inverse transform per row
  (`unrotate_embedding_rows`), and store as `bf16` (2.54 GB) or `q8_g32_fp16` (1.3 GB) exactly like
  the existing artifact stores `embed_tokens`. Zero kernel work; the residual stream receives
  primal-basis embeddings. M5 replaces this with a ternary gather + inverse Hadamard kernel to save
  ~1-2 GB.
- lm_head: emit `q8_g32_fp16` in v1 (existing `linear_topk` q8 kernels); note the lm_head INPUT is
  rotated in Bonsai, so v1 must instead fold the rotation into the dequantized head:
  `W_head = (W' @ H) * s` per block (primal-basis weights, then q8). This is legal only because
  the head is dequantized anyway. M5 switches to a `t2` `linear_topk` kernel with the Hadamard
  prologue and drops the fold.

Weight budget v1: 48 layers × (16384+5120·6144/5120… ) — concretely per layer 2-bit planes
(16384·5120 + 5120·6144 + 34816·5120 + 5120·17408)/4 ≈ 91.1 MB + scales/32 ≈ 2.8 MB → 64 layers ≈
6.0 GB, plus q8 lm_head 1.3 GB, embedding 1.3-2.5 GB, MTP/DFlash2 as today. Fits with room for KV.

## 8. Risks and open questions

1. `ssm_a` convention in the GGUF (`A_log` vs `-exp(A_log)`): resolved by M0's numeric compare.
2. GDN `out_proj` input order in NInfer vs `gdn_v_grouped` (section 5.3). Wrong order = garbage
   only in GDN layers; M0 cannot catch it, M3's token comparison will.
3. q/gate interleave in the fused attention qkv and gate/up order in the fused MLP tensor: reuse
   the converter's existing row assembly; a mistake shows as garbage at M3.
4. PTQ1_0 decode cost is converter-only (CPU numpy, one pass over 6 GB); the runtime never sees
   base-3 data.
5. Chat template: the GGUF embeds one; the existing artifact has the fork's fixed template. Use the
   artifact's unless PrismML changed it (diff both in M1).
6. Standalone Hadamard launches in v1: 4 per layer × 64 = 256 extra launches per token (~0.5–1 ms in
   a graph). Acceptable for M3; M4 fuses them.
7. Accumulation precision: fp32 accumulation everywhere; fp16 scales are exact in fp32.
8. `code == 3` must never appear; the converter asserts it, the kernels may treat it as +2 (as
   llama.cpp's Q2 codec does) rather than branch.

## 9. Resolved during implementation (agents append here)

- (A) Python side of the format, 2026-09-23: format string `t2_g128_fp16` (class
  `TernaryFormat`, group 128), layout string `ternary_row_k128_v1` (alignment 256): plane 0
  codes `N x K/4` bytes row-major, plane 1 FP16 scales `N x K/128` row-major starting at
  `align_up(N*K/4, 256)`; `payload = scale_offset + N*K/128*2`; K must be a multiple of 128;
  no weight divisor. `tools/artifact/layouts.py:ternary_geometry` is the byte geometry the
  C++ `weight_geometry` must reproduce. Sign vectors are the direct bf16 parameters
  `text/hadamard/signs_{5120,6144,17408}`; the config block carries a `signs` map to them
  (section 2).
- (B) C++ enums, 2026-09-24: `QType::T2_G128_FP16 = 9`, `QuantLayout::TernaryRowK128 = 4`
  (`src/core/weight.h`), spellings in `src/artifact/formats.cpp`. `weight_geometry` gives
  `group_size = 128`, `code_bytes_per_row = K/4`, `scale_bytes_per_row = K/64`, scale plane at
  `align_up(N*K/4, 256)`, no high plane, no divisor; `native_weight` accepts whole-row views of
  a fused parent (like RowSplit) with `scale_dtype = FP16`, `scale_ne = {K/128, n}`,
  `scale_nb = {2, K/64}`. `tests/artifact/test_reader.cpp` pins the byte counts of the six 27B
  shapes to the Python geometry.
